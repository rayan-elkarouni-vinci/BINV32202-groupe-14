Parcours d'affichage des offres

Gesta sépare l'interface React, l'API Express, les règles métier et l'accès SQL. Cette page suit une requête de la route /offres jusqu'aux tables SQLite, puis son retour vers le tableau affiché.

Vue d'ensemble

1

Route React

App.tsx rend OffersPage si l'utilisateur est connecté et autorisé à lister les offres.

2

Page et hook

OffersPage.tsx appelle useOffers, qui gère chargement, erreur, annulation et déconnexion sur 401.

3

Appel HTTP

offers.service.ts envoie GET /api/offers avec le jeton dans Authorization.

4

Contrôleur Express

Le proxy Vite retire /api. Le routeur backend authentifie puis autorise avant d'appeler le service d'offres.

5

Service métier

Le profil détermine la visibilité : toutes les offres, les publiées ou celles déposées par le contact.

6

SQL et SQLite

Le repository joint offres, entreprises, années et périodes, trie le résultat et retourne des lignes brutes.

Parcours détaillé

1. Entrée dans l'interface

Dans frontend/src/App.tsx, useAuth fournit l'utilisateur et son jeton. La route /offres n'est créée que si canListOffers(user) est vrai. La page reçoit aussi onUnauthorized, utilisé pour revenir à la connexion quand l'API répond 401.

OffersPage.tsx appelle useOffers(token, onUnauthorized). Selon son état, elle affiche LoadingState, ErrorState, EmptyState ou OfferTable.

2. Hook, service et validation de la réponse

useOffers.ts lance l'appel dans un useEffect et utilise un AbortController lors du démontage. Le service offers.service.ts appelle fetch("/api/offers") et transmet le jeton sans préfixe Bearer.

readJson contrôle le statut HTTP, puis isOfferList vérifie la forme des objets. Le modèle frontend Offer attend notamment academicYear, period et status.

3. Authentification, autorisation et contrôleur

Le proxy défini dans frontend/vite.config.ts transmet /api/offers au backend sous /offers. Dans backend/src/app.ts, le middleware authenticate est exécuté avant le routeur des offres.

authenticate.ts vérifie le jeton et recharge l'utilisateur en base. Ensuite, offers.controller.ts applique authorize(canListOffers). La route transmet l'utilisateur courant au service et convertit chaque résultat en DTO avec toOfferDto.

4. Règles métier

Dans offers.service.ts, visibilityFilter construit le filtre serveur :

  • un administrateur reçoit toutes les offres ;
  • un étudiant reçoit seulement les offres PUBLISHED ;
  • un contact déposant reçoit ses propres offres, quel que soit leur statut ;
  • un contact sans rôle déposant reçoit une erreur 403.

Le service ne connaît ni Request ni Response. Il passe un OfferFilter au repository, puis transforme les lignes SQL en objets métier avec toOffer.

5. Requête SQL et données

offers.repository.ts prépare une requête qui sélectionne les colonnes de offers et joint :

  • companies pour le nom court de l'entreprise ;
  • academic_years pour le libellé de l'année ;
  • periods pour le code P1, P2 ou OTHER.

Le filtre SQL est optionnel pour le statut et le déposant. Le tri se fait par année académique décroissante, puis par date de création décroissante. Le schéma de 001_initial.sql garantit notamment que la période appartient à la même année académique que l'offre.

6. Retour et rendu

Le contrôleur renvoie une liste de DTO contenant uniquement id, title, companyShortName, academicYear, period et status. Le hook place cette liste dans son état, puis OfferTable.tsx rend une ligne par offre. Les codes de période et de statut sont convertis en libellés français par labels.ts.

Ajout d'un filtre par période

Pour un filtre appliqué côté serveur, les fichiers concernés seraient les suivants. Le choix d'un filtre strictement visuel dans le tableau ne garantirait pas la même sémantique et ne réduirait pas les données transmises ; le parcours ci-dessous conserve donc le filtre dans la requête API et dans le repository.

ZoneFichierÉvolution attendue
Interface frontend/src/pages/OffersPage.tsx Ajouter le contrôle de sélection de période et conserver sa valeur dans l'état de la page.
Chargement frontend/src/hooks/useOffers.ts Accepter la période comme paramètre et relancer le chargement quand elle change.
Client HTTP frontend/src/services/offers.service.ts Encoder la période dans la query string, par exemple /api/offers?period=P2.
Contrat frontend frontend/src/models/offer.ts, frontend/src/utils/guards.ts Réutiliser PeriodCode et valider le paramètre avant l'appel ; le DTO de réponse peut rester inchangé.
Contrôleur API backend/src/controllers/offers.controller.ts Lire et valider le paramètre period, retourner 400 INVALID_QUERY s'il est invalide, puis le passer au service.
Règles métier backend/src/services/offers.service.ts Ajouter la période au filtre en conservant le filtre de visibilité propre au profil.
Accès SQL backend/src/repositories/offers.repository.ts Étendre OfferFilter, le paramètre préparé et le WHERE avec p.code ou o.period_id.
Documentation backend/API.md, backend/http/offers.http Documenter le query parameter, ses valeurs autorisées et un exemple de requête.
Tests backend backend/tests/offers.test.ts Couvrir chaque valeur, l'absence de filtre, la combinaison avec les droits et le cas de paramètre invalide.
Tests frontend frontend/tests/OffersPage.test.tsx, éventuellement frontend/tests/helpers/fetchMock.ts Vérifier l'envoi du paramètre, le changement de période, l'affichage vide et la gestion des erreurs.
Point de cohérence : la période est déjà portée par le DTO et contrôlée par PERIOD_CODES. L'ajout du filtre ne nécessite donc pas de migration SQL ; il étend principalement le contrat de requête, le filtre métier et les tests.
