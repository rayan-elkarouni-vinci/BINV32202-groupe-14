Corrections apportées à l'analyse de Copilot

  • Copilot classait en « senseurs inférentiels » les cas de tests manuels, architecture.md et le cahier des charges. C'est inexact :
    • architecture.md et le cahier des charges sont des guides (ils agissent avant) ;
    • les cas de tests manuels relèvent de la boucle humaine (c'est nous qui observons, pas une IA).
  • Copilot listait les contraintes SQLite (CHECK) et les middlewares authenticate / authorize comme senseurs. Ce sont des comportements de l'application, pas des retours sur le travail de l'agent. Ils ne deviennent un retour que lorsqu'un test les vérifie. Nous les avons donc retirés de la matrice.
  • Pas de CI : aucun dossier .github/workflows/. Les senseurs ne tournent que si quelqu'un (nous ou l'agent) lance les commandes localement.

1Architecture serveur Controller → Service → DB ; le serveur porte « logique métier, gestion des données, sécurité » (séance 3, slide « Rappels web1 - Serveur REST » ; séance 6, slide « Serveur »)copilot-instructions.md : « Backend requests flow through controllers -> services -> repositories -> SQLite » et « Keep authorization and data visibility rules in backend services… Frontend permission helpers… must not be the security boundary »OuiRien à ajouter. Le guide va plus loin que Web 2 (couche repositories séparée, mappers), de façon cohérente.
2L'ordre d'enregistrement des middlewares détermine l'ordre d'exécution ; authentification au niveau de la route ; middleware d'erreur (séance 3, slides « Qu'est-ce qu'un middleware ? », « Middleware au niveau route », « Middleware d'erreur »)copilot-instructions.md : « Authentication is applied before protected controllers… Use HttpError for expected failures so errorHandler returns the standard shape »PartielleLe principe est présent, mais rien sur l'ordre de montage. Conséquence observée en semaine 2 : en montant le routeur des candidatures à la racine, Copilot a rendu toutes les routes inconnues authentifiées (401 au lieu de 404), et c'est la suite de tests qui l'a détecté. Ajout proposé : « Monter authenticate au niveau du routeur ou de la route protégée, jamais globalement avant les routes publiques et le 404 ; enregistrer errorHandler en dernier. »
3Ressources au pluriel, sous-ressources (/users/1/orders) ; POST crée, PATCH met à jour partiellement, DELETE supprime (séance 4, slides « Ressources », « Méthodes HTTP », « Méthode et chemin »)Aucun passage sur le nommage des routes ou le choix des méthodes HTTP, ni dans copilot-instructions.md ni dans architecture.mdNon (absent)Nos routes : POST /offers/:offerId/applications respecte la sous-ressource. Le retrait est POST /applications/:id/withdraw : nous avons refusé DELETE (rien n'est supprimé), mais une route d'action n'est pas le style REST du cours, qui suggérerait PATCH /applications/:id sur le statut. Sans consigne dans le guide, ce choix dépend de chaque prompt. Ajout proposé : « Ressources au pluriel ; POST crée, PATCH modifie partiellement, DELETE supprime ; justifier toute route d'action. »
4Codes de statut : 201 après un POST ; 400 données invalides, 401 non authentifié, 403 sans droits, 404 inexistant, 409 conflit (ressource existe déjà) (séance 4, slides « Statut de la réponse » et « Codes d'erreur »)copilot-instructions.md : « Use HttpError for expected failures » et « tests for successful and denied access » ; pull_request_template.md : « cas d'erreur (400, 401, 403, 404…) »PartielleLe guide dit comment signaler une erreur, pas quel code choisir. Le modèle de PR ne cite pas 409, alors que nos doublons et l'offre non publiée en renvoient. Nous utilisons aussi 409 pour OFFER_NOT_PUBLISHED, ce qui va au-delà de la définition du cours (« ressource existe déjà ») : choix défendable (conflit d'état), mais à documenter. Ajout proposé : un tableau « situation → code HTTP → code d'erreur » dans le guide, et 409 dans le modèle de PR.
5En TypeScript, annotation explicite obligatoire des paramètres et des retours de fonctions (séance 2, slide « TypeScript : les types », encadré « Attention »)Aucun passage. .oxlintrc.json interdit any ("typescript/no-explicit-any": "error") et tsconfig est en strict, mais rien n'impose les types de retourNon (absent)Vérifié dans applications.service.ts : les méthodes listOwn, withdraw et apply annotent leurs paramètres et leur retour (: Application[], : Application), mais la fabrique createApplicationsService a un retour inféré. La convention est donc suivie par imitation du code existant, pas parce qu'un guide l'impose. Ajout proposé : « Annoter explicitement les types des paramètres et des retours de fonctions », ou une règle de lint équivalente (senseur computationnel plutôt que guide).

Problèmes trouvés dans les guides eux-mêmes

  • Référence morte : copilot-instructions.md renvoie à « docs/architecture.md », alors que le fichier se trouve dans docs/analyse/architecture.md. Un agent qui suit la consigne à la lettre ne le trouve pas. Correction proposée : mettre à jour le chemin.
  • Incohérence de chemin : pull_request_template.md demande la conversation dans docs/conversation-N.md, alors que les consignes du cours demandent docs/semaine-N/.

Recommandations (par priorité)

  1. Corriger le chemin vers architecture.md : simple, et l'agent lit ce guide à chaque tâche.
  2. Ajouter la règle sur l'ordre des middlewares : un défaut réel est déjà survenu.
  3. Ajouter les conventions REST et le tableau des codes HTTP du cours.
  4. Ajouter l'annotation des types de retour, de préférence sous forme de règle de lint.

Nous n'avons pas modifié les guides : la consigne demande un audit, pas une correction.

Limites de l'audit

  • Seuls les supports de Web 2 cités ci-dessus ont été utilisés ; d'autres séances (formulaires, état React, modules) n'ont pas donné de consigne vérifiable sur les points audités.
  • Le point 5 n'a été vérifié que dans applications.service.ts, pas dans tout le projet.
